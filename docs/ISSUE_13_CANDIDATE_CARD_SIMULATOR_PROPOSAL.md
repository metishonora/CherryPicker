# 후보 카드 피킹률 시뮬레이터 제품 제안

- 문서 상태: **제품 구현 완료 · 병합·배포 승인**
- 작성일: 2026-08-20
- 제품 범위: CherryPicker 로컬 웹 제품
- 작업 식별자: GitHub Issue #13
- GitHub 이슈: [#13 후보 카드 혜택 시뮬레이터](https://github.com/metishonora/CherryPicker/issues/13)
- 승인 상태: 2026-08-20 프로토타입 승인, 제품 구현 승인

> 합성 데이터 기반 격리 프로토타입의 흐름과 계산 표현을 검토했고,
> 2026-08-20 사용자가 이를 재사용 가능한 템플릿으로 승인했다. 제품 구현은
> 특정 카드 정보와 분석 월을 에이전트가 구조화해 전달하는 경계를 따른다.

## 1. 제안 요약

최근 한 달 동안 CherryPicker가 수집한 실제 소비를 후보 카드에 가상으로
배분해, 사용자가 선택한 거래에서 받을 수 있었던 혜택과 피킹률을 즉시
계산하는 `후보 카드 시뮬레이터`를 제안한다.

후보 카드로 모든 거래를 결제했다고 전제하지 않는다. 에이전트가 카드 정책과
거래를 먼저 분석하고, 사용자가 **후보 카드로 옮길 거래를 거래 전체 단위로
체크**한다. 체크 상태, 전월 실적 가정 또는 애매한 거래의 답변이 바뀔 때마다
결정론 계산기가 혜택 여부, 혜택 금액과 피킹률을 다시 계산한다.

이 결과는 미래 소비 예측이나 카드사의 실제 청구 결과가 아니라 다음을 뜻한다.

> 선택한 과거 한 달의 거래가 후보 카드 정책 아래 같은 날짜와 금액으로
> 발생했다면 얻었을 것으로 추정되는 혜택의 재현 결과

## 2. 문제와 목표

### 문제

카드 상품 설명만으로는 새 카드가 사용자의 실제 소비에 얼마나 유리한지 알기
어렵다.

- 업종, 가맹점, 간편결제 경로와 정기결제 여부를 거래별로 다시 판정해야 한다.
- 전월 실적, 실적 제외, 최소 결제금액과 월 한도가 서로 영향을 준다.
- 모든 소비를 새 카드로 옮기는 가정은 실제 카드 배분 방식과 다르다.
- 문자에 담긴 정보만으로 혜택 적용 여부를 확정할 수 없는 거래가 있다.
- 혜택이 큰 거래만 분모에 넣으면 실제 카드 사용 효율보다 피킹률이 과장된다.

### 목표

- 사용자가 전달한 후보 카드 정보를 계산 가능한 정책 스냅샷으로 정리한다.
- 최근 한 달 거래를 후보 카드 기준으로 분류하고 근거를 보여준다.
- 자동 확정할 수 없는 사실만 짧고 구체적으로 질문한다.
- 사용자가 후보 카드로 결제할 거래를 직접 체크할 수 있게 한다.
- 선택 변경 즉시 예상 혜택과 피킹률을 같은 입력에서 재현 가능하게 계산한다.
- 모호성을 숨기지 않고 최소~최대 범위와 그 원인을 보여준다.
- 기존 거래 원본과 현재 카드에 대해 사용자가 확정한 판정을 보존한다.

### 목표가 아닌 것

V1은 미래 소비 패턴을 통계적으로 예측하지 않는다. 관측한 한 달을 다른 카드
정책으로 다시 계산하는 시뮬레이션이며, 카드 발급이나 실제 결제 수단 변경을
대신하지 않는다.

## 3. 용어

| 용어 | 의미 |
| --- | --- |
| 후보 카드 | 사용자가 새로 검토하는 카드. CherryPicker에 보유 카드로 등록돼 있지 않아도 된다. |
| 분석 월 | 시뮬레이션 거래를 가져오는 `Asia/Seoul` 기준 달력 월(매월 1일~말일) |
| 정책 스냅샷 | 특정 출처와 기준일의 카드 정책을 구조화해 고정한 읽기 전용 입력 |
| 거래 사실 | 기존 canonical 거래의 승인 금액, 가맹점, 거래 일시 등 수집·파싱된 값 |
| 후보 카드 분류 | 후보 카드 정책에 대해서만 파생한 실적·혜택 판정 후보와 근거 |
| 확정 분류 | 정책과 거래 사실만으로 한 가지 결과가 나거나 사용자의 답변으로 확정된 분류 |
| 애매한 거래 | 현재 정보로 둘 이상의 정책 적용 결과가 가능한 거래 |
| 선택 거래 | 사용자가 “이 거래는 후보 카드로 결제한다”고 체크한 승인 거래 |
| 선택 승인 총액 | 선택 거래의 승인 금액 합계. 혜택이 0원인 선택 거래도 포함한다. |
| 예상 혜택 | 정책 스냅샷, 거래 분류, 선택 상태와 전월 실적 가정으로 계산한 금액 |
| 관측 월 피킹률 | 예상 혜택을 선택 승인 총액으로 나눈 값 |
| 전월 실적 가정 | 분석 월의 혜택 자격과 한도를 결정하기 위해 사용자가 선택한 직전 월 조건 |
| 계산 적용 순서 | 월 한도나 횟수 제한을 어느 거래와 혜택부터 소진할지 정하는 안정적인 순서 |

## 4. 제품 원칙과 데이터 경계

### 기존 데이터를 수정하지 않는다

시뮬레이션은 기존 데이터를 읽기만 하고 별도 분석 데이터로 저장한다.

- 카드 문자 원문, canonical 거래 사실과 파싱 스냅샷을 수정하지 않는다.
- 현재 보유 카드에 대해 사용자가 확정한 실적 인정·제외, 혜택 선택, 메모와
  집계 제외 상태를 후보 카드 분류로 덮어쓰지 않는다.
- 후보 카드 분류와 질문 답변은 시뮬레이션에 귀속한다.
- 체크를 바꾸거나 시뮬레이션을 삭제해도 원래 거래와 대시보드 집계는 바뀌지
  않는다.
- 후보 카드 정책은 현역 카드 종류 정의에 자동으로 추가하지 않는다.

이 경계는 [제품 아키텍처](PRODUCT_ARCHITECTURE.md)의 거래 사실, 파싱 결과와
사용자값 분리 원칙을 그대로 따른다.

### 사실 재사용과 판정 재사용을 구분한다

기존 거래에서 재사용하는 것은 날짜, 금액, 가맹점과 같은 거래 사실이다.
기존 카드에서 확정한 실적·혜택 판정은 후보 카드의 정책이 다르므로 정답으로
복사하지 않는다. 다만 사용자가 남긴 보조 정보가 거래 사실을 설명하는 경우에는
분류 근거 후보로 보여줄 수 있으며, 자동 확정에 사용하려면 적용 범위를
사용자가 확인해야 한다.

### 개인용 로컬 제품 경계를 유지한다

시뮬레이션은 현재 Swift/Hummingbird/SQLite 로컬 웹 제품과 인증 경계 안에
둔다. 프로토타입과 커밋하는 fixture에는 합성 거래와 합성 카드만 사용한다.

## 5. 역할 분리

| 역할 | 책임 | 하지 않는 일 |
| --- | --- | --- |
| 에이전트 | 후보 카드 자료 해석, 정책 초안 구조화, 거래별 분류 후보와 근거 생성, 꼭 필요한 확인 질문 작성 | 최종 산술 결과를 임의 계산하거나 애매한 사실을 단정하지 않음 |
| 사용자 | 정책 초안 확인, 후보 카드로 옮길 거래 체크, 애매한 사실 답변, 전월 실적 가정 선택 | 카드 약관의 모든 조건을 직접 계산하지 않음 |
| 결정론 계산기 | 확정된 정책 스냅샷과 입력으로 실적, 혜택, 한도 배분, 범위와 피킹률 계산 | 자연어를 해석하거나 알 수 없는 거래 사실을 추측하지 않음 |

에이전트가 같은 입력에 다른 표현을 만들더라도 계산 결과는 바뀌면 안 된다.
금액, 반올림, 경계값과 한도 적용은 모두 구조화된 정책을 입력으로 받는 순수
계산 경계가 소유한다.

## 6. 제안 사용자 흐름

1. 사용자가 후보 카드의 상품명과 상품 설명서, 약관 또는 직접 정리한 혜택
   정보, 분석할 `YYYY-MM`을 전달한다.
2. 에이전트가 출처와 기준일을 남기고 카드 정책 초안을 구조화한다.
3. 에이전트가 계산에 필요한 누락·충돌 조건을 사용자에게 확인하고, 정확히
   표현할 수 있는 정책 스냅샷을 제품에 전달한다.
4. 에이전트가 해당 월의 승인 거래 템플릿을 가져온다.
5. 에이전트가 승인 거래를 후보 카드 정책 기준으로 분류한다.
6. 확실한 거래에는 적용·제외 근거를 표시하고, 애매한 거래는 모아 질문한다.
7. 사용자가 전월 실적 가정을 선택하고 후보 카드로 옮길 거래를 체크한다.
8. 체크, 답변 또는 실적 가정이 바뀔 때마다 결정론 계산기가 전체 선택 집합을
   다시 계산한다.
9. 사용자는 거래별 결과, 총혜택, 관측 월 피킹률, 미확정 범위와 연회비 반영
   보조 지표를 함께 검토한다.
10. V1은 한 번에 후보 카드 한 장과 분석 월 한 개의 현재 초안을 자동 보존해
    정책 스냅샷, 선택 상태, 답변과 계산 버전을 같은 입력으로 다시 열 수 있게
    한다.

정책의 필수 계산 조건은 초안을 전달하기 전에 확정해야 한다. 거래 사실만으로
답할 수 없는 거래 질문은 미응답 상태로도 시뮬레이터를 열 수 있으며, 제품은
이를 0원으로 단정하지 않고 가능한 결과의 최소~최대 범위로 표시한다.

### 에이전트와 제품의 연결 경계

V1은 CherryPicker 안에 별도 대화형 AI나 클라우드 모델 호출을 넣지 않는다.
사용자가 대화 중인 에이전트가 카드 자료를 해석하고, CherryPicker의 인증된
로컬 경계로 구조화한 정책 초안과 분류 근거를 전달하는 흐름을 제안한다.
제품은 그 초안을 읽기 쉬운 형태로 보여주고 사용자의 확인·답변과 계산 입력을
소유한다.

에이전트는 인증된 `GET /api/v1/candidate-simulations/template?month=YYYY-MM`로
월 거래를 받고, 구조화한 정책과 모든 거래의 분류를
`PUT /api/v1/candidate-simulations/current`로 전달한다. 자연어 설명은 계산기에
직접 들어가지 않고 정책 스냅샷 계약을 검증한 뒤에만 계산한다. 자세한 반복
절차는 [후보 카드 시뮬레이션 에이전트 작업 절차](CANDIDATE_CARD_SIMULATION_AGENT_WORKFLOW.md)에
고정한다.

## 7. 후보 카드 정책 스냅샷

정책 스냅샷은 카드 이름만 저장하는 메모가 아니라 계산기 입력 계약이다.
최소한 다음을 포함한다.

### 식별과 출처

- 후보 카드 표시 이름
- 카드사와 상품 식별 정보
- 정책 출처 이름과 참조 위치
- 자료 기준일 또는 적용 기간
- 에이전트가 구조화한 시각과 정책 스냅샷 버전
- 확인된 조건, 사용자가 제공한 조건, 아직 미확정인 조건의 구분

### 실적 정책

- 실적 산정 기간과 혜택 제공 기간의 관계
- 실적 구간별 혜택 자격 또는 한도
- 경계값 포함 방향
- 실적 제외 항목
- 혜택을 받은 결제의 실적 포함 여부
- 할부 금액 산정 방식
- 신규 발급 실적 유예의 기간, 자격과 제공 한도

### 혜택 정책

- 혜택 이름과 표시 순서
- 대상 업종, 가맹점, 결제 경로와 필요한 정기결제 속성
- 건별 최소·최대 금액, 횟수 조건과 기간
- 할인·적립률과 금액 반올림 단위 및 방향
- 혜택별 월 한도, 통합 월 한도와 한도 공유 그룹
- 혜택 중복 허용 여부와 우선순위
- 공통·혜택별 제외 항목
- 전표 매입일 등 승인일 외의 날짜가 필요한 조건

### 비용 정책

- 기본 연회비와 제휴 연회비
- 첫해 면제 또는 프로모션 여부
- 가족카드 등 이번 시뮬레이션에 포함하지 않는 비용의 구분

필수 계산 조건이 자료에 없으면 임의의 관행으로 채우지 않는다. 예를 들어
원 단위 절사 여부나 통합한도 소진 순서가 결과를 바꿀 수 있다면 정책 확인
질문으로 올린다. 답을 얻어 계산 가능한 정책으로 만들기 전에는 초안을
업로드하지 않는다. V1의 최소~최대 범위는 검증된 한 정책 안에서 거래 분류가
둘 이상 가능한 경우에 적용한다.

정책 스냅샷을 만든 뒤 원자료가 바뀌어도 기존 시뮬레이션 결과는 자동으로
달라지지 않는다. 새 자료를 반영할 때는 새 스냅샷 버전을 만들고 다시 계산해
변경 전후를 구분한다.

## 8. 거래 분류와 확인 질문

### 거래별 분류 결과

각 승인 거래에는 후보 카드 기준으로 다음 파생 정보를 둔다.

- 실적 인정 가능 상태: `인정`, `제외`, `애매함`
- 적용 가능한 혜택과 적용 불가능한 혜택
- 필요한 조건 충족 여부: 금액, 업종, 결제 경로, 정기결제, 제외 항목 등
- 확신 상태: 거래 사실로 확정, 사용자 답변으로 확정, 미확정
- 판단 근거가 된 정책 조항과 거래 필드
- 미확정일 때 가능한 분류들과 결과를 갈라놓는 질문

`혜택 대상 아님`과 `실적 제외`는 독립적으로 판정한다. 혜택이 0원이어도
실적에는 인정될 수 있고, 그 반대가 가능한 카드 정책도 표현할 수 있어야 한다.

### 질문 원칙

질문은 계산 결과를 바꾸는 정보에 한정하고, 한 번에 답할 수 있게 작성한다.

- `샘플OTT 13,500원은 월 정기결제였나요?`
- `샘플페이 100,000원은 상품 구매인가요, 선불 잔액 충전인가요?`
- `이 결제는 백화점 안의 임대 매장에서 결제했나요?`

`혜택을 받을 것 같나요?`처럼 정책 판정을 사용자에게 되묻지 않는다. 사용자는
정기결제 여부나 실제 구매 성격처럼 자신만 확인할 수 있는 사실에 답하고,
계산기가 그 사실을 정책에 적용한다.

답변은 기본적으로 해당 거래에만 적용한다. 같은 가맹점의 과거·미래 거래에도
재사용하려면 사용자가 `이 가맹점의 같은 표시 거래에 적용` 같은 별도 범위를
명시적으로 확인해야 한다. 에이전트가 한 거래의 답을 전역 규칙으로 자동
확장하지 않는다.

### 미확정 거래의 범위

애매한 선택 거래는 결과에서 제거하지 않는다. 가능한 분류를 계산기에 전달해
다음처럼 표시한다.

- 거래별 예상 혜택: `0원~6,750원`
- 총 예상 혜택: `10,000원~15,000원`
- 관측 월 피킹률: `2.4%~3.6%`

최솟값은 모든 미확정 조건을 무조건 0원으로 더한 값이 아니라, 알려진 정책과
조건을 지키면서 가능한 가장 낮은 결과다. 최댓값도 각 거래의 독립 최대액을
단순 합산하지 않고, 월 한도와 중복 제한을 함께 적용한 가능한 가장 높은
결과다.

## 9. 거래 선택 규칙

### 승인 거래 전체가 선택 단위다

V1에서 체크박스 하나는 승인 거래 한 건 전체를 뜻한다.

- 체크하면 해당 거래의 승인 금액 전부를 후보 카드 결제로 가정한다.
- 체크를 해제하면 그 거래는 실적, 혜택, 한도와 피킹률 계산에서 모두 빠진다.
- 거래 금액 일부만 후보 카드에 배분하는 기능은 제공하지 않는다.
- 한 거래를 여러 카드로 나누거나 부분 결제한 것으로 만들지 않는다.
- 제품의 기본 선택 상태는 아무 거래도 체크하지 않은 상태를 제안한다. 사용자가
  의도한 배분만 명시적으로 추가하게 하기 위함이다. 프로토타입의 기본 검토
  fixture에서는 계산 변화와 한도 배분을 바로 확인할 수 있도록 거래 일부를
  선택해 두며, 외부 검토 도구에서 `선택 0건` 상태로 전환해 함께 검토한다.

혜택 가능성이 있는 거래만 체크할 수 있게 제한하지 않는다. 혜택 0원이나 실적
제외로 분류된 승인 거래도 사용자가 실제 배분을 재현하기 위해 체크할 수 있다.
이 금액 역시 **선택 승인 총액**과 피킹률 분모에 포함한다.

### 선택 승인 총액과 0건 상태

```text
선택 승인 총액 = 선택한 모든 승인 거래의 승인 금액 합계
```

선택 거래가 0건이면 총혜택은 0원이지만 `0 ÷ 0`을 0%로 표시하지 않는다.
피킹률은 `—`와 `거래를 선택하면 계산됩니다`로 표시한다.

## 10. 전월 실적 가정

대부분의 카드에서 분석 월 혜택 자격은 직전 월 실적으로 결정된다. 분석 월의
선택 거래를 같은 분석 월 혜택 자격에 순환 적용하지 않는다.

V1은 정책 스냅샷에서 파생한 다음 가정 중 하나를 명시적으로 선택하게 한다.

1. `직전 월 실적 없음`: 0원 구간으로 판정한다.
2. `정책에 정의된 실적 구간`: `30만원 달성`, `60만원 달성`처럼 혜택 결과가
   달라지는 경계 중 하나를 선택한다. 카드별 구간은 정책 스냅샷에서 생성한다.
3. `신규 발급 유예 적용`: 정책 스냅샷에 확인된 유예 기간과 한도가 있을 때만
   선택할 수 있다.

정확한 직전 월 인정액이 구간 내부에서 결과를 바꾸는 카드라면 구간 선택 대신
금액 직접 입력을 사용한다. 합성 프로토타입은 결과가 구간에서만 바뀌므로
`미달 / 30만원 / 60만원 / 신규 발급 유예` 선택으로 단순화한다.

선택한 분석 월 거래에서 계산한 `예상 실적 인정액`은 그 달 자체의 혜택
자격을 바꾸는 값이 아니라, 정책상 다음 달 실적 구간을 예상하는 보조 결과로
표시한다. 카드 정책이 전월 실적이 아닌 다른 기준 기간을 사용한다면 정책
스냅샷이 그 관계를 명시하고 계산기는 그 기간을 따른다.

가정 영역에는 입력값뿐 아니라 파생된 혜택 구간과 월 한도를 함께 보여준다.
예를 들어 `직전 월 300,000원 가정 → 이번 달 통합한도 15,000원`처럼 결과에
영향을 주는 관계를 숨기지 않는다.

## 11. 결정론적 계산 규칙

### 날짜와 평가 기간

- 분석 월은 `Asia/Seoul` 기준 매월 1일 00:00을 포함하고 다음 달 1일
  00:00을 포함하지 않는 구간이다.
- V1은 canonical 거래의 거래 일시가 분석 월에 포함되는 승인 거래를 사용한다.
- 혜택과 실적의 월 한도는 정책 스냅샷에 다른 기준이 명시되지 않는 한 같은
  `Asia/Seoul` 달력 월 단위로 초기화한다.
- 승인일 외 매입일이 필수인데 CherryPicker에 그 사실이 없으면 확정으로
  추측하지 않고 애매한 조건으로 남긴다.

### 거래별 계산

선택한 거래마다 다음 순서로 계산한다.

1. 정책 공통 제외와 실적 제외를 각각 판정한다.
2. 혜택별 대상, 결제 경로, 정기결제와 건별 금액 조건을 판정한다.
3. 전월 실적 가정에서 파생된 자격과 한도를 적용한다.
4. 정책의 할인·적립률과 반올림 규칙으로 한도 적용 전 원 계산액을 구한다.
5. 혜택 중복 규칙, 건수 제한, 혜택별 한도와 통합한도를 적용한다.
6. 거래별 실제 배분액과 한도 때문에 받지 못한 금액을 기록한다.

### 한도와 적용 순서

한도 때문에 어떤 거래가 혜택을 받는지가 달라질 수 있으므로 적용 순서는
입력 계약의 일부다.

- 거래는 거래 일시 오름차순으로 적용한다.
- 거래 일시가 같으면 canonical 거래 식별자의 안정적인 오름차순을 사용한다.
- 한 거래가 여러 혜택 후보에 해당하면 정책 스냅샷의 혜택 우선순위와 중복
  규칙을 적용한다.
- 정책이 사용자의 혜택 선택이나 카드사 매입 순서처럼 현재 알 수 없는 순서를
  요구하면 임의로 확정하지 않고 정책 확인 질문으로 올린다.
- 체크박스를 껐다 다시 켜도 적용 순서는 바뀌지 않는다.

계산 결과에는 `한도 적용 전 혜택`, `실제 예상 혜택`, `한도로 받지 못한
금액`을 구분한다. 한 계산 경로의 혜택별 배분액 합계는 거래 예상 혜택과
정확히 같아야 한다. 미응답 대안에 따라 서로 다른 혜택이 배타적으로 적용되어
혜택별 최소·최대를 더할 수 없는 경우에는 혜택별 범위를 합계처럼 나열하지
않고, 상관관계를 보존한 거래 합계 범위만 표시한다.

### 피킹률

기본 지표는 사용자가 체크한 모든 승인 거래를 분모로 한다.

```text
관측 월 피킹률 = 총 예상 혜택 ÷ 선택 승인 총액 × 100
```

- 혜택이 0원인 선택 거래도 분모에 포함한다.
- 실적 제외 거래나 혜택 제외 거래도 선택했다면 분모에 포함한다.
- 체크하지 않은 거래는 분자와 분모 모두에 포함하지 않는다.
- 미확정 결과가 있으면 총혜택의 최소·최대 각각으로 피킹률 범위를 계산한다.
- 통화 계산은 정수 원 단위로 하고, 비율 표시 자릿수는 UI 정책으로 고정한다.

### 연회비 반영 보조 지표

연회비는 월 거래에서 직접 발생한 혜택이 아니므로 기본 피킹률의 분자에서
빼지 않는다. 대신 정책 스냅샷의 확정된 연회비를 12개월로 나눈 보조 지표를
별도로 제안한다.

```text
월 환산 연회비 = 연회비 ÷ 12 후 1원 미만 버림
연회비 반영 월 순혜택 = 총 예상 혜택 - 월 환산 연회비
연회비 반영 보조 피킹률 = 연회비 반영 월 순혜택 ÷ 선택 승인 총액 × 100
```

첫해 면제, 캐시백형 연회비나 월할 불가능한 비용이 있으면 단일 수치로 오해하지
않도록 가정을 함께 표시한다. 이 보조 지표는 기본 `관측 월 피킹률`을 대체하지
않는다.

## 12. 실시간 계산 불변식

프로토타입과 이후 제품 구현은 다음 외부 동작을 만족해야 한다.

| 불변식 | 사용자에게 보이는 결과 |
| --- | --- |
| 동일한 정책 스냅샷, 거래 사실, 답변, 전월 실적 가정과 선택 집합은 항상 같은 결과를 낸다. | 새로고침하거나 체크 순서를 달리해도 금액이 같다. |
| 체크 변경은 전체 선택 집합을 원자적으로 다시 계산한다. | 거래 행과 상단 요약이 서로 다른 이전 상태를 잠시라도 확정 결과처럼 표시하지 않는다. |
| 체크하지 않은 거래는 모든 계산에서 빠진다. | 미선택 거래의 예상 혜택은 참고로 보여도 총액과 한도를 소진하지 않는다. |
| 혜택 0원인 선택 거래도 선택 승인 총액에 포함한다. | 유리한 거래만 분모에 넣어 피킹률을 부풀리지 않는다. |
| 월 한도 적용 후 혜택은 음수가 아니며 해당 한도를 넘지 않는다. | 거래별 배분 합계가 혜택별·통합한도와 총 예상 혜택을 초과하지 않는다. |
| 더할 수 있는 혜택별 배분액 합계는 거래 예상 혜택과 같고, 배타적 대안의 한계 범위는 합계처럼 표시하지 않는다. | 거래 근거와 목록·상단 총액이 서로 모순되지 않는다. |
| 미확정 조건은 하나의 확정 금액으로 숨기지 않는다. | 거래, 총혜택과 피킹률에 최소~최대 및 원인이 함께 보인다. |
| 선택 승인 총액이 0원이면 피킹률을 계산하지 않는다. | `0%`가 아닌 `—`로 표시한다. |
| 전월 실적 가정과 그로부터 정해진 구간·한도를 항상 함께 표시한다. | 사용자가 높은 한도가 어디서 왔는지 확인할 수 있다. |
| 질문 답변을 바꾸면 그 답에 영향받는 분류와 전체 결과를 다시 계산한다. | 이전 답변에서 나온 혜택이 남지 않는다. |
| 시뮬레이션 입력 변경은 원래 거래와 기존 카드 집계를 변경하지 않는다. | 기존 대시보드 값은 전후가 같다. |
| 연회비 보조 지표는 기본 총혜택과 관측 월 피킹률을 변경하지 않는다. | 두 지표의 목적과 계산식이 구분된다. |

구현 단계에서는 순수 도메인 테스트로 금액·경계·순서 불변식을, HTTP 및 제품
경로 테스트로 저장과 원본 비변경을 검증한다. 프로토타입 단계에서는 합성
시나리오로 정보 구조와 상호작용을 검토하되 제품 계산의 최종 증거로 간주하지
않는다.

## 13. V1의 취소 거래 처리

V1에서는 취소 거래를 후보 카드 선택과 계산에서 제외한다. 분석 월에 취소가
있으면 `취소 거래 N건은 이번 시뮬레이션에서 제외됨`을 명시해 빠진 사실을
숨기지 않는다.

이유는 다음과 같다.

- 현재 제품은 취소를 원승인과 연결하지 않는 독립 거래로 처리한다.
- 과거의 취소가 후보 카드로 가상 배분한 어떤 승인에 대응하는지 알 수 없다.
- 원승인 없이 취소만 후보 카드에 배분하면 선택 승인 총액, 실적과 혜택을
  잘못 낮출 수 있다.
- 승인과 취소를 모두 단순 선택하게 하면 사용자가 환불 순서와 한도 복원
  규칙을 직접 재구성해야 하며 V1의 비교 목적보다 복잡성이 커진다.

향후 취소를 포함하려면 후보 카드 가상 원승인과의 연결, 취소 시점의 실적
차감 월, 혜택·한도 복원 순서와 부분 취소 정책을 별도 승인해야 한다. 기존
제품의 독립 취소 정책은 [ADR-0005](adr/0005-independent-cancellation-performance.md)에
그대로 남으며, 시뮬레이터 때문에 변경하지 않는다.

## 14. 제안 화면 구조

### A. 후보 카드 준비

- 후보 카드 이름, 정책 출처와 기준일
- 구조화한 실적 구간, 혜택, 제외 조건, 한도와 연회비 요약
- 계산에 필요한 미확정 정책 경고
- 분석 월 표시
- `거래 분석하기` 주요 동작

정책 원문 전체를 주 화면에 길게 펼치지 않고, 계산에 사용되는 구조화 결과와
근거를 우선 보여준다.

### B. 분류 확인

- `혜택 대상`, `혜택 없음`, `확인 필요` 건수 요약
- 계산 결과를 바꾸는 확인 질문 목록
- 질문마다 대상 거래의 가맹점, 날짜와 금액
- 답변 이후 바뀐 실적·혜택 분류와 근거
- 아직 답하지 않고 시뮬레이터로 이동할 수 있는 동작과 범위 표시 설명

### C. 거래 선택 시뮬레이터

상단에는 후보 카드, 분석 월과 전월 실적 가정을 고정 문맥으로 보여준다.
선택 중에도 결과를 놓치지 않도록 고정 요약에는 다음 핵심 값만 표시한다.

- 선택 승인 총액
- 총 예상 혜택 또는 최소~최대 범위
- 관측 월 피킹률 또는 범위

나머지 계산 근거는 `계산 상세`에서 펼쳐 확인한다.

- 선택 거래 건수와 예상 실적 인정액
- 다음 달 실적 구간 전망
- 월 한도 사용액과 남은 금액
- 연회비 반영 보조 지표

거래는 기존 제품의 한 열 목록 원칙을 따른다. 각 행에는 전체 거래 선택
체크박스, 가맹점, 날짜, 승인 금액, 혜택 상태와 예상 혜택만 우선 표시한다.
실적 상태, 혜택 이름, 한도 전·실제 적용·미수혜 금액과 적용·제외 근거는
행의 `근거 보기`에서 펼친다. 거래를 선택하는 행 영역과 근거를 펼치는 동작은
별도 네이티브 컨트롤로 구분한다.

모바일에서는 요약을 간결하게 유지하고 거래 목록을 한 열로 표시한다. 데스크톱
공간이 넓어도 거래를 카드 그리드로 바꾸지 않는다. 공통 표현과 접근성은
[제품 UI 원칙](PRODUCT_UI_PRINCIPLES.md)을 따른다.

### 저장 동작

V1은 별도 `저장` 화면이나 시나리오 라이브러리를 만들지 않고 현재 후보 카드와
분석 월의 초안 하나를 자동 보존한다. 이는 선택안을 다시 열기 위한 것이며,
기존 거래 검토를 확정하거나 후보 카드를 보유 카드로 등록하는 동작이 아니다.

## 15. 합성 프로토타입 시나리오

프로토타입에는 실제 카드나 실제 거래를 복사하지 않고 다음 합성 정책과 거래를
사용한다.

### 합성 후보 카드 `체리 라이프 카드`

- 직전 월 실적 300,000원 이상이면 분석 월 통합 혜택한도 15,000원,
  600,000원 이상이면 30,000원
- `간편결제 10% 청구할인`, 체리페이 건당 10,000원 이상
- 영상 스트리밍 월 정기결제 50% 할인
- 생활요금 자동납부 5% 할인
- 상품권과 아파트관리비는 혜택과 실적에서 제외
- 전기요금은 혜택 대상이지만 실적에서는 제외
- 신규 발급 유예를 적용하면 300,000원 구간과 같은 15,000원 한도 제공
- 모든 혜택은 하나의 통합한도를 거래 일시순으로 소진
- 연회비 12,000원

### 합성 거래

| 날짜 | 가맹점 | 승인 금액 | 분류 의도 |
| --- | --- | ---: | --- |
| 07-02 | 체리마켓 온라인 | 43,000원 | 혜택 확정, 원 계산액 4,300원 |
| 07-04 | 합성아파트 관리비 | 168,000원 | 혜택·실적 제외지만 선택 가능 |
| 07-07 | 체리플레이 | 13,500원 | 정기결제 혜택 확정, 원 계산액 6,750원 |
| 07-10 | 체리모바일 | 72,400원 | 자동납부 혜택 확정, 원 계산액 3,620원 |
| 07-13 | 오픈마켓 주문 | 95,000원 | 간편결제 여부 질문, 혜택 0원~9,500원 |
| 07-18 | 체리에너지 전기요금 | 86,000원 | 혜택 대상이지만 실적 제외 |
| 07-22 | 체리외국어학원 | 120,000원 | 혜택 없음, 실적 인정 |
| 07-25 | 합성 기프트카드 | 50,000원 | 혜택·실적 제외지만 선택 가능 |
| 07-27 | 체리프레시 | 21,000원 | 혜택 확정, 원 계산액 2,100원 |

### 프로토타입에서 검토할 상태와 동작

1. `선택 0건` 검토 상태에서 피킹률이 `—`로 보인다.
2. 혜택 확정 거래만 선택하면 금액, 한도와 피킹률이 즉시 계산된다.
3. 체리외국어학원처럼 혜택 0원 거래를 추가하면 총혜택은 같고 분모와
   실적만 늘어나 피킹률이 낮아진다.
4. 아파트관리비를 선택하면 실적과 혜택은 늘지 않지만 선택 승인 총액은
   늘어난다.
5. 오픈마켓 주문의 간편결제 여부에 답하지 않은 상태에서는 거래와 전체
   결과가 범위로 보인다.
6. 간편결제 답변을 바꾸면 거래 일시순으로 통합한도가 다시 배분된다.
7. 한도 소진 뒤 거래에는 원 계산액과 한도로 받지 못한 금액이 구분된다.
8. 전월 실적 가정을 300,000원에서 0원으로 바꾸면 혜택 자격과 결과가 함께
   갱신된다.
9. 월 환산 연회비 1,000원을 반영한 보조 지표가 기본 피킹률과 구분된다.

프로토타입의 검토 폭은 최소 320px, 일반적인 iPhone Safari 폭과 736px 이상
데스크톱이다. 검토용 상태 전환 컨트롤은 제품 화면 밖에 두며 제품 구현에
포함하지 않는다.

## 16. V1 제안 범위

### 포함

- 후보 카드 한 장의 정책 스냅샷 작성과 확인
- `Asia/Seoul` 기준 달력 월 한 개 선택
- 해당 월의 기존 승인 거래 사실 읽기
- 후보 카드 기준 거래 분류와 근거
- 계산 결과를 바꾸는 애매한 거래 질문과 거래 단위 답변
- 승인 거래 전체 단위 체크와 선택 상태 저장
- 전월 실적 가정 선택
- 결정론적 실적, 혜택, 한도, 피킹률과 범위 계산
- 연회비 월 환산 보조 지표
- 원본 및 기존 카드 판정 비변경
- 합성 데이터 기반 반응형 웹 프로토타입

### 제외

- 여러 후보 카드의 동시 비교와 포트폴리오 최적화
- 저장한 여러 선택안을 복제·비교하는 시나리오 라이브러리
- “가장 유리한 거래를 자동 선택”하는 자동 최적화
- 거래 금액 일부 선택, 분할 결제와 여러 카드 자동 배분
- 취소, 부분 취소와 원승인 연결
- 미래 소비·계절성·연간 소비의 통계적 예측
- 카드사 청구서와 실제 지급 혜택의 자동 대사
- 카드 약관의 무인 자동 확정이나 출처 없는 정책 보완
- 카드사·마이데이터 외부 연동, 카드 신청이나 발급
- 후보 카드 정책을 현역 카드 정의로 자동 등록
- 다중 사용자와 외부 공개 공유

`어떤 거래를 체크하면 최대 혜택인가`를 계산하는 자동 최적화는 의도적으로
제외한다. V1의 주된 일은 사용자가 현실적으로 옮길 거래를 직접 선택하고 그
배분의 결과를 이해하는 것이다. 최적화는 목표 함수, 필수 유지 카드, 카드별
실적과 분할 가능성 등 별도 제품 결정을 요구한다.

## 17. 승인과 구현 게이트

게이트 1~4는 2026-08-20에 통과했고, 사용자가 구현 브랜치의 병합·푸시·배포를
승인했다.

### 게이트 1: 제안 검토 · 완료

- 문제, 계산 분모, 전월 실적 가정, 애매함 표현과 V1 범위를 검토했다.
- 아래 제품 결정을 승인 기록에 반영했다.

### 게이트 2: 격리 프로토타입 검토 · 완료

- 에이전트가 구조화한 합성 정책 초안 확인, 거래 질문, 체크와 실시간 재계산
  흐름을 만든다.
- 모바일과 데스크톱에서 선택·범위·한도 정보를 오해하지 않는지 확인한다.
- 에이전트에게 자료를 보내는 대화 UI, 여러 저장안을 관리하는 화면과 필터는
  이번 프로토타입에 포함하지 않는다.
- 합성 거래 fixture는 2026년 7월 한 달로 고정하며, 분석 월을 바꿔 다른
  거래를 불러오는 동작은 제품 구현 단계의 계약과 테스트에서 검증한다.
- 사용자가 수정 요청 반영본을 검토하고 프로토타입을 승인했다.
- 프로토타입 승인은 화면 기준선이며 제품 계산 구현의 정확성 증거는 아니다.

### 게이트 3: 구현 범위 확정 · 완료

- 승인된 프로토타입과 제품 결정을 문서에 기록했다.
- GitHub Issue [#13](https://github.com/metishonora/CherryPicker/issues/13)을 생성했다.
- 후보 카드 전용 Core, API, SQLite와 제품 UI 경계를 식별했다.
- 계산 불변식을 순수 도메인, 저장 재시작, HTTP와 제품 경로 증거에 매핑했다.

### 게이트 4: 제품 구현과 검증 · 완료

- 후보 카드 전용 결정론 계산기, 불변 정책 스냅샷과 현재 초안 저장, 월 거래
  템플릿·PUT·GET·PATCH API와 제품 UI를 연결했다.
- 순수 계산기는 선택·실적·혜택·한도·미응답 범위·연회비를 검증하고, 혜택
  상태와 실적 상태를 분리해 기존 카드 집계를 변경하지 않는다.
- HTTP 검증은 인증·CSRF, canonical 사실 재결합, 오래된 변경 요청 거부,
  저장 재시작과 기존 거래·대시보드 비변경을 합성 데이터로 확인한다.
- 전체 Swift 패키지 테스트는 Server 75개와 Core 54개가 모두 통과했다.
- 승인된 프로토타입의 JavaScript와 제품 JavaScript 구문, 문서의 합성 요청
  계약을 함께 검증했다. 제품 브라우저 시각 자동화는 실행 환경이 없어 별도
  검토 항목으로 남기고, 실제 인증 제품 루트의 조합 경로까지 자동 검증했다.

## 18. 프로토타입 검토 결정

프로토타입 승인과 구현 요청에 따라 V1은 다음처럼 확정한다.

1. 분석 기간은 `Asia/Seoul` 기준 달력 월로 고정한다.
2. 제품의 초기 거래 선택은 모두 해제로 둔다.
3. 질문에 답하지 않아도 범위 상태로 거래 선택을 시작할 수 있다.
4. 거래 질문의 답은 해당 거래에만 적용하고 같은 가맹점으로 자동 확장하지 않는다.
5. 전월 실적은 정책 결과가 달라지는 구간 선택을 기본으로 한다.
6. 연회비 반영 보조 지표는 `계산 상세`에 둔다.
7. V1은 원자료 파일 대신 출처 메타데이터와 검증된 구조화 정책을 보존한다.
8. 애매한 결과는 별도 `확정 금액` 없이 최소~최대 범위로 표시한다.
9. 거래별 근거는 기본 접힘인 네이티브 상세로 제공한다.

## 19. 승인된 구현 연결 경계

- 에이전트는 인증된 월별 승인 거래 템플릿을 조회하고, 후보 카드 정책과 거래별
  분류·질문을 구조화해 로컬 API로 전달한다.
- 제품 안에는 별도 대화형 AI나 외부 모델 호출을 넣지 않는다.
- 정책 스냅샷과 진행 중 초안은 후보 카드 전용 SQLite 테이블에 저장한다.
- 계산 결과는 저장하지 않고 Swift Core의 순수 계산기가 입력에서 매번 파생한다.
- 브라우저 변경 요청은 화면이 읽은 초안 ID와 상태를 함께 보내며, 그 사이 새
  초안이나 더 최신 상태가 저장되었으면 이전 요청을 거부한다.
- 기존 카드 정의, 거래 검토, 혜택 판정과 대시보드는 읽거나 변경하지 않는다.
- 제품은 한 번에 현재 초안 하나를 보여주며 여러 저장안을 관리하는 UI는 만들지
  않는다.
